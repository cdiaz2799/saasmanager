# Database package instructions

Applies to `packages/db/**`, in addition to the root instructions. Use the
`db-schema-change` skill (`.claude/skills/db-schema-change/SKILL.md`) for any
schema edit, and `supabase-postgres-best-practices` before writing SQL.

## Layout

- `src/schema/` — table definitions. `shared.ts` holds the tenant primitives,
  `enum.ts` every `pgEnum` (53 of them), `auth.generated.ts` the Better Auth
  tables, and `tables.ts` the aggregate `tables` object.
- `src/relations.ts` — `defineRelations(tables, ...)` for the relational query API.
- `src/tenant.ts` — tenant resolution and the scoped transaction helper.
- `src/runtime.ts` — `assertRuntimeDatabase()`, the startup safety check.
- `src/auth.ts` — auth-only models/relations, kept separate so Better Auth's
  `usePlural: true` does not collide with the domain `accounts` table.
- `src/migrations/` — drizzle-kit output (not the drizzle default directory).
- `sql/001-runtime-role.sql` — privilege and FORCE-RLS hardening, applied by hand
  after migrations.

## Two table families

1. **Better Auth tables** (`auth.generated.ts`) — UUID ids, plain `timestamp`,
   shapes dictated by the adapter. Generated by `bun run auth:generate`; never
   hand-edit and never restyle them.
2. **Domain tables** (`catalog.ts`, `commercial.ts`, `technical.ts`,
   `integrations.ts`, `ingestion.ts`, `audit.ts`) — the multi-tenant model.

## Domain table pattern

Every domain table is built from the same three pieces. Copy an existing table
rather than assembling one from scratch.

```ts
export const things = pgTable.withRLS(
  "things",
  { ...recordColumns(), /* table-specific columns */ },
  (t): PgTableExtraConfigValue[] => [...recordConstraints("things", t)]
);
```

- `pgTable.withRLS(...)` — not plain `pgTable`. A domain table without RLS fails
  startup validation.
- `recordColumns()` (`shared.ts`) — `id` (uuid, `defaultRandom`), `tenantId`
  (FK to `tenants`, `onDelete: "restrict"`), `createdAt`, `updatedAt`, `revision`
  (integer, default 1). It is a factory: call it per table, don't share the object.
- `recordConstraints(name, t)` (`shared.ts`) — the `(tenant_id, id)` unique, the
  `revision >= 1` check, `(tenant_id, created_at, id)` and
  `(tenant_id, updated_at, id)` indexes, and `tenantPolicy(t.tenantId)`. Passing
  the wrong `name` silently produces mismatched constraint names in the migration.

`tenantPolicy` compares the column against
`nullif(current_setting('app.tenant_id', true), '')::uuid` for both `using` and
`with check`, so an unset GUC matches no rows rather than all rows.

### Shared entity identity

Catalog entities that participate in shared identity (`vendor`, `product`,
`application`, `instance`, `person`, `group`, `service_principal`, `account`,
`contract`, `subscription`, `entitlement`, `technical_asset` — the `entityKind`
enum) carry a `kind` column and use `entityConstraints(name, t, kind)` from
`catalog.ts` instead of `recordConstraints`. It adds a `kind = '<kind>'` check and
a composite FK on `(tenant_id, id, kind)` back to `entity_registry`.

Enforcement of *exactly one* matching typed row per registry row is not
implemented in SQL — the FK permits a registry row with no typed row. Code that
resolves a registry entry must handle the missing-row case rather than assuming it.

### Conventions

- All enums live in `enum.ts`. Do not declare `pgEnum` in a table file.
- Register every new table in `tables.ts` and every new relation in
  `relations.ts`. `tables` drives both `assertRuntimeDatabase()` and the relational
  API, so an unregistered table skips startup validation and `.query` joins on an
  unregistered relation silently return nothing.
- Relations join on composite `(tenantId, id)` pairs, never on `id` alone.
- `$inferSelect` / `$inferInsert` are internal persistence types, not public DTOs.

## revision / updatedAt are not yet maintained

`revision` and `updatedAt` default to `1` and `now()` at insert and **nothing
updates them** — there are no triggers in `src/migrations/` or `sql/`, and
`shared.ts` marks the maintenance as pending. Until that is resolved, a write path
that needs an accurate revision must set it explicitly and atomically in the same
statement (`set revision = revision + 1, updated_at = now() where ... and revision = $n`).
Do not assume optimistic concurrency works by itself, and do not add an
application-code trigger substitute without deciding the approach with the user.

## Optional runtime hardening check (`assertRuntimeDatabase`)

`assertRuntimeDatabase` is a test/deployment verification helper; the server does
not invoke it at startup. It verifies that, for every table in `tables`:

- the runtime login has no membership in any `SUPERUSER`, `BYPASSRLS`, or
  `CREATEROLE` role;
- row security is enabled and forced (or the login does not own the table);
- the login holds `SELECT`/`INSERT`/`UPDATE`/`DELETE` but **not** `TRUNCATE`;
- the table has **exactly one** policy, named `tenant_isolation`, `for all`, with
  both a `using` and a `with check` expression.

The exactly-one-policy rule is the easy one to trip: adding a second policy makes
the optional check fail even if the policy is harmless. Update
`sql/001-runtime-role.sql` when grants change and apply it after migrating.

## Tenant access helpers (`src/tenant.ts`)

- `resolveTenantMembership(db, userId, organizationId)` → `forbidden` (not a
  member), `unavailable` (no tenant provisioned yet), or `ready` with `membership`
  + `tenantId`. This is what turns a requested org selection into an authorized
  `tenantId`; a selector alone is never authority.
- `withTenantTransaction(db, tenantId, cb)` — opens a transaction with the
  `app.tenant_id` GUC set via `set_config(..., true)` so RLS applies. All
  tenant-scoped work goes through it. Never use a session-level `SET` on a pooled
  connection, and never use the global `db` inside the callback.
- `provisionOrganizationTenant(db, organizationId)` — trusted server only, never
  reachable from an endpoint. Locks the org row and is idempotent; the auth hook
  that calls it is not atomic with organization creation, so retries are expected.

Keep all callback work awaited and materialize results before returning. Do not
hold a transaction open across a vendor network call or return a deferred
query/stream from it.

`organization-tenant.ts` maps one Better Auth organization ID to one domain tenant
UUID. It is server-only, must never be accepted from client input or returned to a
client, and the runtime login is granted only `SELECT, INSERT` on it — no updates
or deletes.

## Migrations

`drizzle.config.ts` reads `DATABASE_URL` from `apps/server/.env` (not
`packages/db/.env`) and writes to `./src/migrations`. The server can use a trusted
server-only elevated login for both migrations and runtime. A normal
non-`BYPASSRLS` role is optional defense in depth, not a runtime requirement.

- `bun run db:generate` → review the generated SQL before applying. Drizzle will
  happily emit a destructive rename as drop + create.
- `bun run db:migrate` → then apply `sql/001-runtime-role.sql` → then restart.
- `bun run db:push` is local prototyping only, never against the shared Supabase DB.

## Testing

`bun test packages/db/test/tenant.test.ts` covers organizations, membership,
provisioning, RLS, scoped transactions, and OpenAPI boundaries. It needs the
disposable PostgreSQL fixture described in `docs/tenant-isolation.md`. Use at
least two tenants for any isolation test — a single-tenant test passes even when
the policy is missing entirely.
